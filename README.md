# 饭飞来 · 校园外卖履约协同系统

> 基于真实运转的学生自配送体系，完成的完整产品案例：业务分析 → 产品规划 → 产品设计 → 可交互原型 → 验证方案
>
> A full product case study on digitizing a real, student-run campus delivery network — business analysis, product planning, PRD, interactive prototype, and validation plan.

## 背景

广东财经大学三水校区存在一个**真实自组织运转**的学生外卖配送体系：20+ 校内外商家以 2.5 元/单的价格，将外卖配送委托给学生团队（10+ 骑手 + 50-60 名上楼学生 + 园区负责人），覆盖 7 大园区 22 栋宿舍楼，日均数千单。

它完全靠"社会契约"运转：微信群共享表格排班、纸质小票作为送达凭证与工资依据、人工周结对账——**一行代码都没有，但商业闭环真实成立**。

本案例以配送团队成员的一线视角，对该体系完成调研与解构，并输出数字化协同产品方案。核心原则：

- **不重构业务模式**——批次制、分账结构、商家自配送模式全部保留；
- **只做协同层数字化**——电子核销替代撕小票，自动分账替代人工数票，批次可视化替代状态黑箱；
- **数据可得性决定路径**——订单数据锁在平台侧，所以 MVP 先做内部结算协同，再做用户端追踪。

## 核心设计：一单 2.5 元的三级分账

```
商家支付 2.5 元/单
 ├─→ 骑手        1.0 元   干线：商家 → 园区分餐点
 ├─→ 上楼学生    1.2 元   末端：分餐点 → 宿舍门口（30 分钟一批）
 └─→ 学生负责人  0.3 元   组织 / 排班 / 对账 / 收款
```

末端定价高于干线（1.2 > 1.0）——价格真实反映了劳动强度排序，这是该体系最值得学习的自组织定价智慧。

## 在线体验原型

直接打开 [04-产品原型-Demo.html](04-产品原型-Demo.html)（单文件，无需任何依赖），建议按这条链路操作，可以体验完整的跨端状态联动：

1. **用户端**：点「餐没到？催单」——工单直达负责人，替代原来"用户→商家→园区群→学生"的四跳链路；
2. **负责人端**：工单池实时出现催单，点「处理」，回执自动发给用户；
3. **骑手端**：点「送达分餐点」——用户端进度条自动推进；
4. **上楼学生端**：逐单点「核销 +1.2」——电子核销替代撕小票，实时计入个人流水；
5. 全部核销后回到**用户端**：进度走到「核销完成」。

（原型内为模拟数据，仅演示核心交互闭环。）

## 方法论亮点

- **需求零假设**：全部痛点来自亲历观察与角色访谈，而非虚构场景；
- **尊重运营约束**：保留 30 分钟批次制——它是该体系履约成本近零的核心，数字化只做可视化，不做颠覆；
- **MVP 取舍有据**：内部对账协同（数据自主可控）先于用户端追踪（数据锁在平台侧）；
- **量化验证闭环**：为每个痛点定义可测量的验证指标（核销准确率、周对账人时、催单率、异常处理时长）。

## 数据诚实度说明

- 结构性规模（22 栋 / 7 园区 / 20+ 商家 / 60+ 人）为调研确认的真实数据；
- 日均单量采用运力交叉验证估算（骑手运力上限法），并规划以一周小票实物计数校准——**宁可保守，不编数字**。
